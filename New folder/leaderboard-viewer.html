Why “no login” cannot reach the old board

  1. The scores live behind an account-scoped API. Play Games Services exposes them at games/v1/leaderboards/{id}/scores/{collection}, and every call requires an OAuth 2 access token that asserts a Google identity with the https://www.googleapis.com/auth/games scope.
  2. API keys are explicitly rejected. Adding ?key=… returns 401 — “API keys are not supported by this API”. There is no public read path and no anonymous collection.
  3. The board is not a web page. Play Games never published leaderboards as crawlable HTML or a public JSON feed, so there is nothing to scrape or index.
  4. So this page tries anyway. It sends the real request without credentials and shows the exact 401. If you have a token, the advanced field lets the same request go through.
  5. What is actually readable is the replacement board. The game moved its scores to a Firebase Realtime Database. This project's security rules require an authenticated principal, but an anonymous session is issued silently — no user interaction, no login UI. The viewer opens one and reads /scores directly.
  6. Google web cookies do not change this. SID, HSID, SSID, APISID and SAPISID are scoped to .google.com and are not sent to *.googleapis.com; the API's auth config lists OAuth2 only. Worse, those cookies are full account session credentials — never paste them into a web page. The supported bridge from an existing Google session is a short-lived OAuth access token (see the Play Games tab).

The Play Games leaderboard IDs decode to app 175629185577: CgkIqeTCoo4FEAIQAg = board 2 (normal), CgkIqeTCoo4FEAIQAw = board 3 (hard). Achievements from the same app also live under that ID prefix.
